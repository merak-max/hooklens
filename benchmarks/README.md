# Reproducible signed-capture benchmark

Run `pnpm install --frozen-lockfile && pnpm build` first, then:

```sh
pnpm benchmark --requests 3000 --warmup 1000 --concurrency 4 --output /tmp/hooklens-c4.json
pnpm benchmark --requests 3000 --warmup 1000 --concurrency 8 --output /tmp/hooklens-c8.json
```

The harness starts an isolated server process on an ephemeral loopback port and
uses a newly created temporary directory. It never reads the development data
file, contacts a database, or performs outbound replay. It removes only its own
temporary capture data afterward. Management authentication is enabled, and
each capture has a valid HMAC signature. Schema comparison runs on every event.

Warmup fills the default 1,000-event retention window. Throughput and latency
cover only measured requests; latency includes reading and validating the complete HTTP response.
Every response must be 202 with a distinct event ID. Retained signatures and
event counts are checked; any failure makes the command exit nonzero.

This is a closed-loop client and a separate server process on the **same host**.
It uses 111-byte JSON payloads, no connected SSE viewers, no search/replay load,
and an explicitly raised capture rate limit. Reports include the actual byte
count, runtime, logical CPUs, percentiles, errors and server peak RSS. The host
is shared development hardware without CPU or storage isolation.

Persistence is a bounded JSON snapshot rewritten for every accepted event,
followed by atomic rename. **There is no fsync and no crash-durability claim.**
The write queue serializes changes and allows at most 64 pending operations.
This is neither a database benchmark nor comparable durability to the auction
engine's synchronous PostgreSQL results. Higher concurrency may increase queueing
rather than throughput. These measurements establish a baseline, not an SLO.

Raw reports in this directory are generated by the harness, not hand-entered.

## September 27, 2026 reference runs

Linux/ARM64, eight logical CPUs, Node 24.21.0; one independent server process
per run, 1,000 warmups and 3,000 measured requests, no errors:

| Report | Clients | Requests/sec | p99 | Server peak RSS |
| --- | ---: | ---: | ---: | ---: |
| [signed-c4.json](signed-c4.json) | 4 | 107.87 | 44.45 ms | 277,432 KiB |
| [signed-c8.json](signed-c8.json) | 8 | 106.74 | 82.92 ms | 273,792 KiB |

The process rewrites a full snapshot for each event. Doubling clients does not
increase throughput here; it increases queueing. A storage redesign should be
measured against these same workloads before making a performance claim.
